# Аналіз наданих fetch-запитів

Ви знайшли три запити. Для монітора підходить тільки той, який читає дані про талони і не змінює стан у системі.

## 1. `GET https://eqn.hsc.gov.ua/api/v2/tickets`

Це найкращий кандидат для першої перевірки.

Чому:

- метод `GET`;
- очікується `application/json`;
- адреса виглядає як API-ендпойнт для отримання `tickets`;
- немає тіла запиту;
- немає очевидної дії бронювання або підтвердження.

Що ще треба перевірити в браузері:

- що у вкладці `Response` справді повертається список талонів або поточних доступностей;
- чи це не список ваших уже створених записів;
- чи змінюється відповідь, коли ви переходите на екран пошуку практичного іспиту;
- чи є окремі запити для області, сервісного центру, категорії, дати або типу іспиту.

Для `.env` достатньо почати так:

```env
MVS_REQUEST_METHOD=GET
MVS_REQUEST_URL=https://eqn.hsc.gov.ua/api/v2/tickets
MVS_REQUEST_HEADERS_JSON={"accept":"application/json, text/plain, */*"}
MVS_COOKIE_HEADER=ваш Cookie з поточної сесії
```

Браузерні заголовки `sec-ch-ua`, `sec-fetch-*`, `priority`, `accept-language` для першої спроби не потрібні. Якщо сервер відхилить мінімальний запит, їх можна додавати по одному і дивитися, який саме має значення.

## 2. `GET https://eqn.hsc.gov.ua/cabinet/queue?_rsc=...`

Це схоже на службовий запит Next.js React Server Components для підвантаження сторінки кабінету.

Його можна використовувати тільки для аналізу інтерфейсу, але не як основне джерело даних, якщо є нормальний JSON API. Такі `_rsc`-запити часто нестабільні: параметр може змінюватися між сесіями або збірками фронтенду, а формат відповіді не призначений для інтеграцій.

## 3. `POST https://eqn.hsc.gov.ua/...` з великим обфускованим `body`

Цей запит не використовуємо.

Причини:

- URL випадковий або обфускований;
- тіло запиту явно схоже на службовий/захисний payload;
- це `POST`, тобто потенційно може бути повʼязаний із захистом, телеметрією, перевіркою браузера або іншою дією;
- відтворення такого запиту може виглядати як спроба обходу захисту.

Для нашої задачі він не потрібен: бот має читати тільки стабільний read-only API після легального ручного входу.

## Наступний крок

Потрібен не сам `fetch`, а вміст вкладки `Response` для `GET /api/v2/tickets`.

Перед тим як ділитися відповіддю, замаскуйте:

- ПІБ;
- телефон;
- email;
- ідентифікатори користувача;
- cookies, токени і session id;
- номери талонів, якщо вони вже належать вам.

Якщо `GET /api/v2/tickets` повертає не доступні для запису талони, а лише ваші існуючі записи, потрібно в `Network` відфільтрувати запити, які зʼявляються саме після вибору послуги, сервісного центру, категорії і дати.

## Оновлений кандидат: `GET /api/v2/equeue/days`

Запит:

```text
https://eqn.hsc.gov.ua/api/v2/equeue/days?serviceId=43&departmentId=93
```

Це кращий кандидат для монітора, ніж `GET /api/v2/tickets`, бо він зʼявився саме під час відкриття календаря бронювання практичного іспиту для потрібного сервісного центру.

Що означають параметри за спостереженням з інтерфейсу:

- `serviceId=43` - обрана послуга, імовірно практичний іспит;
- `departmentId=93` - конкретний сервісний центр;
- відповідь має показати дні, які календар може підсвітити як доступні.

Стартове налаштування `.env`:

```env
MVS_REQUEST_METHOD=GET
MVS_REQUEST_URL=https://eqn.hsc.gov.ua/api/v2/equeue/days?serviceId=43&departmentId=93
MVS_REQUEST_HEADERS_JSON={"accept":"application/json, text/plain, */*"}
MVS_COOKIE_HEADER=ваш Cookie з поточної сесії
```

Наступне, що треба подивитися у браузері: вкладку `Response` саме для цього запиту. Якщо там порожній масив `[]`, це зазвичай означає, що доступних днів немає. Якщо там є дати або масив обʼєктів, це вже сигнал для сповіщення.

## Другий read-only крок: `GET /api/v2/equeue/slots`

Після вибору дня календар робить запит:

```text
https://eqn.hsc.gov.ua/api/v2/equeue/slots?serviceId=43&departmentId=93&date=2026-06-30T00:00:00
```

Це теж підходить для монітора, бо це `GET` і він лише читає доступні часові вікна для конкретної дати. Відповідь має формат:

```json
{
  "data": [
    {
      "startTime": "09:20:00",
      "stopTime": "09:40:00"
    }
  ]
}
```

Тому правильна read-only архітектура така:

1. Запитати доступні дні через `/equeue/days`.
2. Для кожного дня запитати слоти через `/equeue/slots`.
3. Якщо слоти є, надіслати повідомлення.
4. Запис виконати вручну в браузері.

## Запит бронювання не використовуємо

`POST https://eqn.hsc.gov.ua/api/v2/booking` є дією бронювання. Він містить `x-csrf-token`, короткоживучий `token`, повну конфігурацію послуги, сервісного центру, дня і слота.

У цей проєкт його не додаємо з трьох причин:

- це вже не моніторинг, а зміна стану в системі;
- токени є секретами і мають короткий строк дії;
- користувач має виконувати запис вручну після сповіщення.
